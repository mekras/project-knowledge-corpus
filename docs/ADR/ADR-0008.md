# ADR-0008: Ручное закрытие глобальной стадии прохода без исполнителя

Статус: Принято
Дата: 2026-09-16
Участники: пользователь проекта, software-architect (проектирование), менеджер
задачи (оформление и приёмка следа)

## Контекст

Полный проход конвейера после стадии `verification` обязан пройти глобальные
стадии `concepts`, `impact_audit`, `apply_changes` и `corpus_validation`.
Очередь такой стадии всегда содержит синтетическую задачу, пока стадия не
попадёт в `completed_global_stages` состояния прохода. Эта отметка выставляется
только автоматически — после успешного выполнения зарегистрированной в
`operations.yml` проектной команды. Если для стадии команда не зарегистрирована,
контроллер (`run-corpus-operations.py`) возвращает `executor_not_configured` и
не даёт пути её закрыть.

При этом `kc-pipeline/SKILL.md` прямо предписывает агенту в этом случае не
считать это блокером прохода, а выполнить содержательную работу самому через
профильный навык (`kc-concepts`, `kc-impact-audit` и другие) и «снова построить
очередь». Штатного способа сообщить контроллеру, что стадия закрыта такой
ручной работой, не существует. Обнаруженный обход — прямая правка
`completed_global_stages` в файле состояния прохода, нигде не описанная как
штатная процедура. Это расхождение между инструкцией навыка и договором
инструмента: агент, следующий `SKILL.md` дословно, не может довести полный
проход до статуса `completed` без недокументированной ручной правки состояния.

Решение затрагивает переносимый CLI-контракт `run-corpus-operations.py`, формат
файла состояния прохода и инструкцию `kc-pipeline/SKILL.md`. Оно установлено
как продолжение ADR-0001 (исполняемый договор автономного прохода) и должно
быть с ним согласовано. Отмена решения потребует убрать команду закрытия из
CLI и вернуть проекты-потребители к прежнему тупику или к недокументированной
правке состояния.

Приоритеты сравнения заданы правилами проекта: совместимость публичных
договоров, влияние на пользователей и их рабочие процессы, риск ошибок и
потери данных, затем обратимость.

## Рассмотренные варианты

### Неявное закрытие через существующий `--run-commands` без сконфигурированных команд

Достоинство — не добавляет новый флаг. Недостаток — меняет смысл уже
существующего режима (сегодня он ничего не сообщает состоянию прохода и
успешно завершается при пустом списке команд), то есть вызовы, работающие
сегодня одним образом, начали бы молча менять состояние прохода. Это нарушает
совместимость публичного контракта.

### Файл-маркер вне `state.json`

Достоинство — не трогает формат существующего файла состояния. Недостаток —
создаёт второй источник истины: пришлось бы читать его в `build_run_queues`,
синхронизировать с блокировкой состояния и с валидацией, очищать при новом
`run_id`. Усложняет и планирование, и сверку состояния.

### Автоматический вывод завершения глобальной стадии из артефактов корпуса

Достоинство — концептуально устраняет асимметрию между первичными очередями
(которые контроллер выводит из состояния корпуса) и глобальными (которые
выводятся только из отметки в состоянии прохода). Недостаток — требует заранее
определить обязательные машиночитаемые артефакты для четырёх разнородных
стадий, включая `apply_changes`, что является отдельным крупным изменением
договора корпуса, выходящим за границы текущего дефекта.

### Явная отдельная команда закрытия с проверяемыми предусловиями

Достоинства — явное, наблюдаемое действие; отдельный аддитивный участок
контракта состояния, не меняющий поведение существующих режимов; предусловия
не дают закрыть стадию, для которой есть настроенный, но проваливающийся
исполнитель. Недостаток — добавляет новую точку входа CLI, требующую
документирования и тестов.

### Контроллер сам считает стадию без команды выполненной

Отклонён без рассмотрения альтернатив: даёт ложное завершение стадии без
фактической работы, что не совместимо с целью прохода (проверяемый результат
на каждом этапе).

## Решение

Принят четвёртый вариант. В `run-corpus-operations.py` добавляется отдельный
режим:

```
run-corpus-operations.py <корпус> --operations <файл> \
  --complete-global-stage <concepts|impact_audit|apply_changes|corpus_validation> \
  --evidence <репо-относительный путь> [--evidence ...] [--note "<текст>"] \
  [--state <путь>]
```

Режим только записывает отметку в `completed_global_stages` файла состояния и
не выполняет команд, не меняет содержимое корпуса. Он несовместим с
`--run-pipeline`, `--run-commands`, `--run-adapters`, `--reconcile-state`,
`--rebuild-indexes` и требует `--operations`.

Перед записью проверяются все условия:

1. Стадия — одна из `GLOBAL_STAGES`.
2. Для стадии в `operations.yml` не зарегистрирована команда
   (`configured_commands` пуст). Если команда есть, режим отказывает и
   направляет либо чинить исполнитель, либо осознанно снять команду через
   `kc-setup`. Это ключевая защита: ручное закрытие не может маскировать сбой
   реально настроенного исполнителя.
3. Состояние прохода существует, возобновляемо, не в статусе `completed`, без
   признаков живого параллельного исполнения.
4. Первичный контур очередей пуст, и закрываемая стадия — первая незакрытая
   среди глобальных по установленному порядку. Нарушение порядка отклоняется.
5. Указан минимум один `--evidence`, и каждый путь существует внутри корня
   корпуса. Это единственное проверяемое механически подтверждение, что стадия
   действительно чем-то закрыта, а не пропущена.
6. Повторный вызов для уже закрытой стадии безопасен: не меняет состояние,
   завершается успешно.

Файл состояния получает новый необязательный ключ `global_stage_completions`
(словарь `стадия → {completed_by: "manual", completed_at, evidence, note}`).
Ключи этого словаря — подмножество `completed_global_stages`. Отсутствие записи
для стадии означает, что она закрыта проектной командой. Формат аддитивный:
старые файлы состояния без ключа остаются валидными, старые версии скрипта
читают новый файл без ошибки.

`kc-pipeline/SKILL.md`, `references/operations-contract.md` и
`assets/operations.yml` уточняются: агент обязан закрывать глобальную стадию
без исполнителя именно этой командой с путём к оставленному артефакту, прямая
правка файла состояния запрещена явно.

Остаточный риск принят: контроллер не оценивает качество ручной работы, только
факт существования указанного артефакта. Итоговая операционная проверка перед
статусом `completed` выполняется контроллером независимо и не отменяется
ручным закрытием отдельной стадии.

`--evidence` сделан обязательным, а не предупреждением: это единственная часть
условия, которую можно проверить механически, необязательный вариант обесценил
бы саму защиту.

## Последствия

- у агентов появляется штатный, документированный способ закрыть содержательную
  глобальную стадию, выполненную без проектной команды, вместо недокументированной
  правки состояния;
- существующие вызовы CLI и ранее сохранённые файлы состояния не меняют
  поведения;
- в состоянии прохода и в локальном отчёте появляется видимый след, кто и чем
  закрыл стадию вручную;
- реализация требует новой функции и ветки в `run-corpus-operations.py`, правок
  `read_run_state`, `start_run_state`, `render_report`, набора новых тестов и
  синхронных правок `kc-pipeline/SKILL.md`, `operations-contract.md`,
  `operations.yml`;
- заметное пользователям изменение CLI требует записи в `CHANGELOG.md`.

Решение принято пользователем в диалоге по предъявленному архитектурному
разбору: рассмотренные варианты, точные условия допустимости и два открытых
пункта (принятие остаточного риска отсутствия проверки качества ручной работы;
обязательность `--evidence`) были показаны явно, пользователь утвердил
предъявленный вариант целиком без замечаний. Отдельного второго взгляда не
требовалось, так как решение принято владельцем полномочий напрямую.

## Проверка

Тесты `tools/test-corpus-operations.py` покрывают: закрытие стадии без команды
переводит очередь дальше; отказ при настроенной команде; отказ при непустом
первичном контуре; отказ при нарушении порядка глобальных стадий; отказ без
существующего `--evidence`; безопасный повторный вызов; отказ при статусе
`completed`; отклонение записи `global_stage_completions` для стадии, которой
нет в `completed_global_stages`. Полная коллекция проверяется `apm run tests`.

Решение следует пересмотреть, если ручное закрытие всех четырёх глобальных
стадий станет обычной практикой и артефакты стадий будут стандартизированы —
тогда стоит вернуться к выводу завершения из артефактов корпуса и убрать
отдельную команду. Также пересмотреть, если появятся случаи закрытия стадии без
содержательной работы, не выявляемые итоговой операционной проверкой — тогда
усилить условие 5 проверкой, что артефакт изменён в течение текущего прохода.
