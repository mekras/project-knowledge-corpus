# ADR-0015: Изоляция сбоя проектной команды по единице первичного контура

Статус: Принято
Дата: 2026-11-19

## Контекст

Команды стадий из `operations.yml` получают от контроллера только стадию, а
единицы выбирают сами: обрабатывают всю очередь или одну следующую единицу за
запуск. Ненулевой код любой команды переводит весь проход в `failed` с причиной
`stage_command_failed`. Другие очереди, другие источники и глобальные стадии в
этой попытке не выполняются.

Следующая попытка начинает с той же очереди. Если команда сама выбирает
первую необработанную единицу, она снова берёт ту же сбойную единицу. Одна
постоянно сбойная единица останавливает проход до ручного вмешательства. Так
устроены, например, команды получения у одного из проектов-потребителей: они
обрабатывают одну выбранную единицу за запуск.

Требования ФТ-015 (критерий 5) и БТ-003 (критерий 5) требуют, чтобы сбой
обработки одной единицы откладывал только зависящие от неё задачи. ФТ-022
требует довести остальную работу до глобальных стадий и завершить попытку
состоянием, которое отличается от `completed`, ошибки и ожидания решения
человека. ADR-0014 решил это только для обновления индексов: команды
первичного контура он не затрагивает.

Выбор меняет договор команд стадий и код завершения, на который могут
опираться сценарии проектов-потребителей.

## Факторы сравнения

Порядок задан в `AGENTS.md`: совместимость публичных контрактов, влияние на
пользователей и их рабочие процессы, риск ошибок, миграций и потери данных,
обратимость.

## Рассмотренные варианты

### 1. Сохранить остановку прохода

Договор не меняется, но одна сбойная единица останавливает все источники.
Вариант не выполняет ФТ-015 и БТ-003.

### 2. Откладывать оставшуюся очередь целиком

При ненулевом коде команды первичной очереди контроллер откладывает все
оставшиеся задачи этой очереди до следующей попытки и продолжает другие
очереди и глобальные стадии.

Достоинства:

1. Не требует изменений в командах проектов.
2. Другие очереди и глобальные стадии продолжаются.

Недостатки:

1. Контроллер не знает, какая единица дала сбой, и откладывает задачи всех
   источников этой очереди.
2. Команда, которая сама выбирает следующую единицу, при каждой попытке снова
   упирается в ту же единицу. Остальные задачи очереди не выполняются никогда.
3. Систематическую поломку команды легко принять за временную. Её нужно явно
   показывать в сводке как сбой, а не как ограничение среды.

### 3. Запуск команды по одной единице

Команда объявляет `scope: unit`. Контроллер запускает её отдельно для каждой
задачи очереди и передаёт строго проверенные параметры `{unit_id}`,
`{source_id}` и `{unit_path}`. Ненулевой код, отказ запуска или отсутствие
продвижения откладывают только эту единицу, остальные задачи продолжаются.

Достоинства:

1. Контроллер точно знает сбойную единицу и откладывает только её.
2. Договор для команды простой: одна единица на входе.
3. Подходит командам, которые уже работают по одной единице.

Недостатки:

1. Расширение договора команд. Чтобы получить изоляцию, проект должен
   научить команду принимать единицу.
2. Отдельный процесс на каждую единицу. Пакетная команда теряет пакетную
   обработку.

### 4. Протокол поединичного результата

Контроллер передаёт команде файл со списком задач, а команда записывает файл
результата с итогом по каждой единице: выполнено, сбой с видом и причиной.

Достоинства:

1. Изоляция по единице без отказа от пакетной обработки.

Недостатки:

1. Самый сложный договор: два новых файла, проверка заявленных итогов по
   фактическим изменениям, новые виды ошибок команды.
2. Требует наибольших доработок команд проектов.

## Решение

Приняты варианты 3 и 2 вместе: запуск по единице даёт точную изоляцию, а
откладывание очереди служит запасным порядком для команд без `scope: unit`.
Вариант 4 отложен на случай, если пакетным командам понадобится изоляция.

1. **Область.** Решение действует для очередей первичного контура. Сбой
   глобальной стадии, запись за пределами `write_paths` и нарушение
   `propose_only` по-прежнему переводят проход в `failed`: продолжение после
   нарушения границы записи может умножить вред.
2. **Запуск по единице.** Для команды с `scope: unit` контроллер проверяет
   параметры по допустимому шаблону идентификатора и пути внутри корня
   корпуса. Он запускает команду для каждой задачи очереди и после каждой
   единицы заново строит очередь. Сбой, отказ запуска или отсутствие
   продвижения откладывают только эту единицу.
3. **Запасной порядок.** Для команды без `scope: unit` сбой или отсутствие
   продвижения откладывают оставшиеся задачи этой очереди. Сводка советует
   перевести команду на `scope: unit`.
4. **Вид отложенной работы.** Ненулевой код и отсутствие продвижения получают
   вид `failure`. Отказ запуска из-за отсутствующего инструмента получает вид
   `environment` (ФТ-015). Запись хранит очередь, единицу, команду, код
   завершения и число подряд неудачных попыток. Запись живёт только в локальном
   состоянии прохода, вывод команды — только в локальном отчёте (ДТ-015,
   критерий 5).
5. **Повтор.** Каждая новая попытка заново пробует отложенные задачи. После
   двух подряд неудачных попыток по той же единице сводка помечает сбой как
   повторяющийся. В решения человека он автоматически не переводится:
   исправление относится к команде проекта, а не к выбору владельца.
6. **Итог попытки.** Если после глобальных стадий осталась отложенная работа,
   попытка завершается `environment_limited` с кодом `21`. Так ADR-0014 уже
   поступает с непроверенными источниками вида `failure`. Сводка владельца
   перечисляет отложенные единицы с видом и причиной.
7. **Без отката.** Контроллер по-прежнему не откатывает частичные изменения
   сбойной команды. Команда обязана допускать безопасный повтор.

## Последствия

Разовые затраты: расширение договора команд и контроллера, тесты сбоя одной
единицы, примечание к обновлению. Сценарии, которые проверяют код `1` при сбое
команды первичной очереди, получат `21`.

Для пользователей: проход доходит до глобальных стадий при сбое отдельной
единицы. Полная изоляция требует перевести команду на `scope: unit`. До этого
сбой откладывает очередь целиком.

Риски: систематически сломанная команда при каждой попытке даёт `21` вместо
`1`. Ограничение — вид `failure`, счётчик повторов и рекомендация в сводке.

Обратимость: `scope: unit` добавляется, не меняя смысла существующих полей.
Откат возвращает остановку прохода без потери данных корпуса.

## Проверка

Тесты публичного CLI воспроизводят:

- сбой команды `scope: unit` на одной единице при успешной обработке других
  единиц и источников;
- отказ запуска команды из-за отсутствующего инструмента;
- запасной порядок для команды без `scope: unit`;
- повтор отложенной единицы в следующей попытке и счётчик повторов;
- сохранение `failed` для сбоя глобальной стадии и записи за пределами
  `write_paths`.

## Условие пересмотра

Пересмотреть решение, если:

- пакетным командам понадобится изоляция по единице без отказа от пакетов;
- запасной порядок систематически скрывает поломку команд;
- накладные расходы запуска по единице станут заметными для больших очередей.
