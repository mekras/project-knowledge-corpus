# ADR-0009: Карта охвата длинного источника в критерии завершения прохода

Статус: Принято
Дата: 2026-09-16
Участники: пользователь проекта, software-architect (проектирование), программист
(реализация и приёмочный след)

## Контекст

`kc-pipeline/references/workflow-contract.md` формулирует главный инвариант:
«Полный проход движет каждый источник по ближайшей незавершённой стадии», и
отдельно для содержательных источников — «Неизвлечённая структурная единица
без блокера держит стадию открытой так же, как незаблокированный хвост на
другой стадии». Терминальное состояние `completed` ограничено: «`completed`
допустим только при пустых автоматических и внешних очередях».

В проекте-потребителе полный проход объявил `completed`, хотя в
`source-map.yml` длинного источника (`long_source: true`) остались структурные
единицы (условно `*-remainder`) со статусом `deferred` без кода блокера из
закрытого перечня. Причина воспроизводима в коде: планировщик
`run-corpus-operations.py` строил очереди только из `item.yml`/`items.yml` и
никогда не читал `source-map.yml` — карта охвата длинного источника физически
не могла повлиять на решение о `completed`. Дополнительно валидатор раскладки
корпуса для статуса `postponed` в карте охвата требовал только произвольный
текст `reason`, не проверяя код блокера, и допускал статусы вне проверяемого
множества (в инциденте использован `deferred`, который вообще не входит в
проверяемое множество).

Решение затрагивает переносимый CLI-контракт `run-corpus-operations.py`,
схему `source-map.yml`, проверяемую `validate-corpus-layout.py`, и инструкции
`kc-pipeline`. Отмена решения потребует вернуть проекты-потребители к прежнему
разрыву между картой охвата и критерием `completed`.

Приоритеты сравнения заданы правилами проекта: совместимость публичных
договоров, влияние на пользователей и их рабочие процессы, риск ошибок и
потери данных, затем обратимость.

## Рассмотренные варианты

### Постфлайт-проверка после факта

Отдельная проверка карты охвата уже после завершения прохода. Достоинство —
не меняет контур планирования. Недостаток — обнаруживает проблему слишком
поздно: проход, а возможно и зависящие от него глобальные стадии, уже
обработали корпус как полный, и агент не может доработать пробел в том же
проходе, в котором он возник.

### Только исправление схемы валидатора без изменения планировщика

Достоинство — минимальное изменение, ограниченное одним файлом. Недостаток —
не влияет на критерий `completed`: `run-corpus-operations.py` по-прежнему не
читает `source-map.yml`, поэтому проход с незакрытой картой охвата всё равно
может получить `completed`. Недостаточно как самостоятельное решение.

### Молчаливое признание длинного источника завершённым без карты охвата

Статус-кво, приведший к инциденту. Отклонён без дальнейшего рассмотрения:
противоречит главному инварианту и не даёт механической защиты.

### Новая автоматическая очередь `coverage_gap`, встроенная в общий критерий `completed`

Планировщик строит очередь `coverage_gap` из `source-map.yml` каждого
источника с `long_source: true`, сопоставляя `structure.units` и
`coverage.units`. Достоинства — использует уже существующий механизм: критерий
`completed` определён как пустота всех очередей `QUEUE_ORDER`, поэтому
включение `coverage_gap` в этот список закрывает разрыв без отдельной ветки
условия; расположение рядом с `statements` сохраняет для агента ту же модель
работы, что и для очереди без настроенного исполнителя. Недостаток — требует
новой функции чтения `source-map.yml` в переносимом планировщике и синхронной
правки схемы, проверяемой валидатором.

## Решение

Принят четвёртый вариант.

В `run-corpus-operations.py`:

- `QUEUE_ORDER` получает новую очередь `coverage_gap` сразу после
  `statements`; будучи частью `QUEUE_ORDER`, она автоматически входит в
  `PRIMARY_QUEUES` и `AUTOMATED_QUEUES` и учитывается в решении о `completed`,
  `paused_resources` и `waiting_external` без отдельной ветки условия;
- функция `coverage_gap_tasks` для каждого источника с `long_source: true` и
  существующим `source-map.yml` рядом читает `structure.units[].id` (ожидаемые
  единицы) и `coverage.units[]` (записи охвата, ключ `unit_id`);
- ожидаемая единица без записи в `coverage.units`, либо со статусом не из
  `{extracted, no_significant_content, postponed}`, либо со статусом
  `postponed` без валидного `blocker_code` из закрытого перечня становится
  задачей очереди `coverage_gap`;
- единица `postponed` с валидным `blocker_code` уходит в уже существующую
  очередь `human_decision`, с теми же полями (`blocker_code`,
  `action_required`, `automatic_attempts`), что и для заблокированного
  `item.yml`;
- для `blocker_code` из `{access_unavailable, source_unavailable}`
  переиспользуется существующая функция `validate_access_escalation` — та же,
  что уже требует не менее двух сохранённых автоматических попыток для
  `item.yml` и `statements.yml`;
- источник с `long_source: true`, но без `source-map.yml` на диске, не
  создаёт задач `coverage_gap` — это отдельный существующий шлюз
  (`source-map.yml` обязателен на границе нормализации), не относящийся к
  этому решению;
- источник без `long_source: true` не участвует в этой проверке вообще.

В `validate-corpus-layout.py`:

- допустимые статусы `coverage.units[].status` сужены до закрытого перечня
  `{extracted, no_significant_content, postponed}` (с учётом уже
  использовавшегося написания `отложено` как синонима `postponed`); любая
  другая строка, включая `deferred`, — ошибка договора;
- для `postponed` вызывается уже существующая функция `validate_blocker_code`
  с `required=True`, вместо прежней самодельной проверки только `reason`;
  `reason` остаётся обязательным для `postponed`, как и раньше.

Синхронно обновлены: шаблон `.apm/skills/kc-inventory/assets/source-map.yml`
(пример `postponed`-единицы с `blocker_code`, `action_required`,
`automatic_attempts`), `kc-inventory/references/corpus-layout-contract.md`,
`kc-pipeline/references/workflow-contract.md` (отрицательный пример
неверного рассуждения), `kc-pipeline/SKILL.md` и
`kc-pipeline/references/operations-contract.md`.

Остаточный риск принят: планировщик не оценивает качество извлечения внутри
единицы, отмеченной `extracted`, — только факт записи статуса. Это тот же
класс остаточного риска, что уже принят для `item.yml` и `statements.yml`, и
не расширяется этим решением.

## Последствия

- проход не может получить `completed`, пока в `source-map.yml` длинного
  источника остаётся структурная единица без корректной записи охвата;
- у агента появляется штатная очередь `coverage_gap` с той же моделью работы
  без настроенного исполнителя, что и у `statements`;
- незаблокированный хвост длинного источника больше не может быть тихо
  назван «отдельной стадией конвейера» и пропущен при подсчёте `completed`;
- схема `source-map.yml` становится строже: самодельные статусы и `postponed`
  без кода блокера — ошибка договора, а не предупреждение;
- заметное пользователям изменение CLI и схемы корпуса требует записи в
  `CHANGELOG.md`.

## Проверка

Тесты `tools/test-corpus-operations.py` покрывают: единицу без записи в
`coverage.units` → `coverage_gap`; `postponed` без `blocker_code` →
`coverage_gap`; `postponed` с валидным `blocker_code` → `human_decision` с
корректным `action_required`; `postponed` с `blocker_code` из
`{access_unavailable, source_unavailable}` без двух сохранённых попыток →
ошибка договора; источник без `long_source: true` не создаёт `coverage_gap`
при неполной карте охвата; полный проход с закрытой картой охвата и пустыми
прочими очередями → `completed`; полный проход с одной незакрытой единицей →
не `completed`.

Тесты `tools/test-corpus-layout-validator.py` покрывают: `deferred` (или
другой недопустимый статус) → ошибка договора; `postponed` без `blocker_code`
→ ошибка договора; `postponed` с кодом вне закрытого перечня → ошибка
договора.

Полная коллекция проверяется `apm run tests`.

Решение следует пересмотреть, если проекты-потребители начнут описывать
охват длинных источников на уровне отдельных фрагментов внутри одной
структурной единицы — тогда стоит вернуться к более мелкой единице учёта
охвата, чем `structure.units[].id`.
